Версия 0.3 (ЭТАП 0, сверено с ТЗ и аудитом текущего сайта), 2026-11-09. Основание: ТЗ (`ТЗ_ГосАрхивВКО.docx`, 21 с.), рекомендации организаторов хакатона, мастер-бриф, аудит e-arhiv.vko.gov.kz (`source/site-audit/`). Ссылки на ТЗ даны как `§раздел, с. страница`; идентификаторы требований — из `requirements-matrix.md`.

## 1. Критические ограничения

Эти ограничения важнее удобства реализации. Нарушение любого из них считается критической ошибкой этапа.

1. **Сайт информационно-справочный** (ТЗ §1, с. 2; §5.4, с. 7). Нет услуг (в том числе платных), заявлений и архивных запросов, заказов, регистрации официальных обращений, платежей, прейскурантов и кабинетов для заказов (S-020). Для услуг даются только ссылки на официальные каналы. **Разрешены отзывы, предложения и пожелания** (рекомендации организаторов, F-160): форма явно помечена как неофициальная.
2. **Три уровня доступа** (ТЗ §5.3, с. 6; Q-05): `open` — метаданные и цифровая копия; `restricted` — только информационная карточка с описанием и условиями доступа, без копии; `closed` — не публикуется вообще. Закрытые материалы и мастер-копии никогда не попадают в публичный контур: ни в публичный API, ни в публичный бакет, ни в поисковый индекс, ни в контекст ИИ (F-043, F-047, S-016, S-030).
3. **Достоверность.** Ни один выдуманный шифр или факт не показывается как реальный. Каждая запись имеет `data_origin` (`verified` / `demo` / `synthetic`), демо и синтетика видимо помечены (F-044, I-007).
4. **Локализация данных.** Все prod-компоненты self-hosted и разворачиваются в РК. Никаких обязательных зарубежных SaaS для хранения или обработки (P-001, P-002). Утверждение «локализация достигнута» допустимо только после документального подтверждения площадки.
5. **Доступность — свойство основного интерфейса**, а не отдельной версии сайта. Цель WCAG 2.2 AA.
6. **Права проверяются на сервере.** Фронтенд скрывает недоступные действия только для удобства.
7. **Нет фиктивных API.** Mock-данные живут только в сид-наборах и тестовых фикстурах; production-код всегда ходит в БД.
8. **Публикация только через согласование** (ТЗ §6.7, с. 15): черновик → на проверке → требует доработки / одобрено → опубликовано → архивировано. Переходы проверяет сервер (F-150, F-151).
9. **Результаты ИИ — только предложения.** Всё, что сгенерировано ИИ (OCR, аннотации, переводы, категории), сохраняется как черновик и публикуется только после подтверждения сотрудником (ТЗ §5.8 Г, с. 11; §5.9, с. 12).
10. **Перенос данных без потерь** (ТЗ §11, с. 21): импорт сохраняет исходную запись целиком (`raw_import`) и её идентификатор в исходной системе.

## 3. Общая схема

```
                    ┌──────────────────────────── Nginx (TLS, статика, кэш) ─────────────────────────┐
 Браузер ─HTTPS──►  │  /            → SPA (frontend, собранная статика)                              │
                    │  /api/        → backend (Fastify)                                              │
                    │  /media/      → MinIO bucket public-media (только производные открытых записей)│
                    │  /sitemap.xml, /robots.txt, мета-рендер публичных карточек → backend           │
                    └────────────────────────────────────────────────────────────────────────────────┘
                                         │                          │
                         ┌───────────────┴───────┐        ┌─────────┴──────────┐
                         │ backend (Node/Fastify)│──────► │ ai-service (Node)  │──► LLM-сервер (локальный,
                         │ REST API, RBAC, аудит │  HTTP  │ RAG, эмбеддинги    │    OpenAI-совместимый API:
                         └──┬────────────┬───────┘ внутр. └────────┬───────────┘    Ollama / vLLM)
                            │            │                         │
                   ┌────────┴───┐   ┌────┴──────────────┐          │
                   │ PostgreSQL │   │ MinIO             │          │ только чтение публичного
                   │ + pg_trgm  │◄──┤ archive-masters   │          │ представления БД
                   │ + pgvector │   │ (закрытый)        │◄─────────┘
                   └────────────┘   │ public-media      │
                                    └───────────────────┘
```

Решения:

- **Один язык на сервере и клиенте (TypeScript).** Zod-схемы в общем пакете `packages/shared` используются и в формах, и в API. Это убирает дублирование валидации (правило Б§5.1.3).
- **ai-service отдельным процессом**, но на том же языке. Причина: изоляция тяжёлой и медленной нагрузки, отдельные лимиты, возможность вынести на GPU-узел. Python не добавляем, пока не потребуется конкретная библиотека: один человек поддерживает один стек.
- **Монорепозиторий на npm workspaces** (без Nx/Turborepo: для одного разработчика это лишняя абстракция).

## 5. Frontend

**Стек:** React, TypeScript (strict), Vite, Tailwind CSS, shadcn/ui (Radix), React Router (data router), TanStack Query, React Hook Form + Zod, i18next, Lucide React. Карта: Leaflet через `react-leaflet`. Других UI-библиотек не добавляем.

**Слои внутри фичи:**

```
features/catalog/
  api.ts          # функции запросов к REST (единственное место, знающее URL)
  queries.ts      # хуки TanStack Query (ключи, кэш)
  schemas.ts      # схема URL-параметров поиска (реэкспорт из shared)
  components/     # SearchBar, FilterPanel, ResultList, DocumentCard …
```

Правила:

- Компоненты не знают про URL API: только через `queries.ts`.
- Серверное состояние живёт в TanStack Query; глобальный клиентский стейт ограничен тремя контекстами: язык, тема, настройки доступности. Redux/Zustand не нужны.
- Состояние поиска каталога хранится в URL (`useSearchParams`), парсится Zod-схемой; некорректные параметры отбрасываются, а не ломают страницу.
- Все маршруты lazy, админка — отдельный чанк, Leaflet и просмотрщик подгружаются только на своих страницах.
- Единый `apiClient` нормализует ошибки к `{ code, message, details }`; UI показывает переведённое сообщение по `code`.
- Анимации только через утилиту, учитывающую настройку движения (см. accessibility.md §7).

**Компоненты-состояния** для каждой выдачи: `Loading` (скелетон без мигания), `Empty` (что сделать дальше), `Error` (что случилось и кнопка «Повторить»).

## 6. Backend

**Стек:** Node.js LTS, TypeScript strict, Fastify, Zod (`fastify-type-provider-zod`), Prisma, `@fastify/cookie`, `@fastify/rate-limit`, `@fastify/helmet`, `@fastify/multipart`, `argon2`, `file-type`, `sharp`, S3-клиент (`@aws-sdk/client-s3`, работает с MinIO).

**Модуль = маршруты + сервис + репозиторий:**

```
modules/documents/
  documents.routes.ts     # HTTP: схемы, права, коды ответов
  documents.service.ts    # бизнес-правила (публикация, проверка доступа, аудит)
  documents.repository.ts # Prisma-запросы
```

Маршруты не обращаются к Prisma напрямую; сервисы не знают про HTTP.

**Публичный слой доступа.** Все публичные запросы идут через репозиторий-фильтр `publicScope()`, который добавляет условия `publication_status = 'published' AND access_level IN ('open','restricted')` и проверяет, что родительские фонд, опись и дело опубликованы и не закрыты. Второй фильтр `publicCopyScope()` разрешает выдачу цифровой копии только при эффективном `access_level = 'open'` и разрешении на публикацию копии. Для `restricted` отдаются метаданные и `access_conditions`, но не файлы. Админ-модули используют отдельные методы. Так правила доступа описаны в одном месте.

**Ошибки.** Пользователь никогда не видит трассировку или внутренние пути (текущий сайт их показывает, см. аудит). Единый обработчик: ошибки Zod → 400 с полями; доменные ошибки (`NotFound`, `Forbidden`, `Conflict`) → соответствующие коды; всё прочее → 500 без стека наружу, со стеком в журнал. Формат описан в api-design.md §2.

**Авторизация.**

- Серверные сессии в таблице `sessions`; cookie `sid` с `HttpOnly; Secure; SameSite=Strict; Path=/`. Причина выбора вместо JWT: мгновенный отзыв сессии, нет хранения токена в JS.
- CSRF: `SameSite=Strict` + проверка `Origin`/`Referer` + double-submit токен в заголовке `X-CSRF-Token` для POST/PUT/PATCH/DELETE.
- Пароли: argon2id. Блокировка после серии неудачных входов + rate limit.
- Второй фактор (TOTP) — перспектива, заложено поле в `users`.

**RBAC.** Права вида `ресурс:действие` (`documents:read`, `documents:write`, `documents:publish`, `users:manage`, `audit:read` …). Роль = набор прав. Назначение роли пользователю может быть ограничено филиалом (`user_roles.branch_id`), что даёт роль «администратор филиала» без отдельного кода. Проверка — хук `requirePermission(perm, { scopeFrom })`.

Роли по ТЗ §6.1, с. 13 (права настраиваются главным администратором, F-142):

| Роль | Полномочия по ТЗ | Начальный набор прав | В прототипе |
|---|---|---|---|
| Главный администратор | Полный доступ ко всем модулям и настройкам (§6.2, с. 13–14) | все | да |
| Администратор сайта | Страницы, пользователи, настройки контента | `pages:*`, `menu:*`, `settings:write`, `users:manage` (кроме главного администратора), `feedback:*` | да |
| Редактор | Создание, редактирование и публикация информационных материалов | `news:*`, `publications:*`, `exhibitions:*`, `collections:*`, `*:review`, `*:publish` | да |
| Сотрудник архива | Каталог и архивные материалы в пределах полномочий | `fonds/inventories/cases/documents:write`, `assets:upload`, `catalog:import`, `*:submit` (без публикации) | да |
| Администратор филиала | Информация конкретного филиала | права сотрудника и `branches:write` с областью `branch_id` | структура, демонстрация при наличии времени |
| Модератор | Проверка и согласование перед публикацией | `*:review` (вернуть на доработку, одобрить), `feedback:moderate` | да (может совпадать с редактором в демо) |
| Аналитик | Статистика и аналитические отчёты | `analytics:read`, `dashboard:read` | структура |

**Согласование публикаций** (ТЗ §6.7, с. 15). Статусы и переходы:

```
draft ──submit──► in_review ──request_changes──► needs_changes ──submit──► in_review
                      │
                      └──approve──► approved ──publish──► published ──archive──► archived
                                                              ▲                     │
                                                              └──────restore────────┘
```

Каждый переход — отдельный эндпоинт с собственным правом, пишется в журнал и создаёт уведомление (`notifications`) для ролей, которые должны действовать дальше. Редактирование опубликованного материала создаёт новую редакцию в статусе `draft`, а опубликованная версия остаётся на сайте до одобрения изменений (таблица `content_revisions`). Для прототипа допустим упрощённый вариант: правка опубликованного материала возвращает его в `in_review` с сохранением публичной версии (решение уточнить на ЭТАПЕ 10).

**Журнал действий** (ТЗ §6.8, с. 15). Сервис `audit.record()` вызывается внутри той же транзакции, что и изменение: дата и время, пользователь, действие, запись, описание на человеческом языке, IP, краткий diff изменённых полей (без паролей и токенов). Отдельно журналируются вход, выход, неудачные попытки входа, изменения прав и системных настроек.

**Сессии** (ТЗ §7.3, с. 16): скользящий тайм-аут неактивности (по умолчанию 30 минут) и абсолютный срок (12 часов); за 2 минуты до истечения админка предлагает продлить. Ограничение попыток входа: rate limit по IP и логину, после 5 неудач — блокировка учётки на 15 минут.

## 7. SEO для одностраничного приложения

Полный SSR усложняет проект для одного разработчика. Компромисс:

- Nginx для путей публичных карточек (`/{lang}/catalog/:id`, `/history/:slug`, `/news/:slug`, `/exhibitions/:slug`, `/branches/:slug`) проксирует запрос в `backend /seo/render`, который берёт `index.html` и подставляет `<title>`, `meta description`, Open Graph, `link rel=alternate hreflang`, `canonical` и краткое текстовое содержимое в `<noscript>`. Для закрытых и несуществующих записей — 404 и `noindex`.
- `sitemap.xml` генерируется из опубликованных открытых записей на всех языках с переводами.
- `robots.txt` закрывает `/admin` и `/api`. Админка отдаёт `X-Robots-Tag: noindex`.
- Структурированные данные JSON-LD (ТЗ §7.5, с. 17): `GovernmentOrganization` для архива и филиалов, `ArchiveComponent` для документов и дел, `Person` для персоналий, `NewsArticle`, `ExhibitionEvent`, `BreadcrumbList`.
- Ключевые слова (ТЗ §7.5, с. 17): поле `seo_keywords` в переводах публичных сущностей, редактируется в админке.
- ТЗ не требует SSR; если на защите понадобится, переход на SSR (Vike или React Router framework mode) — отдельное решение.

**Сделано на ЭТАПЕ 13 (2026-11-10):** в браузере `usePageMeta` ставит `title`, `description` (у новостей, публикаций и выставок — из анонса), Open Graph, `robots: noindex` для «не найдено» и поиска; `LangLayout` — `canonical` и `hreflang` kk/ru/en/x-default (`lib/head.ts`). Сборка создаёт `robots.txt` и при заданном `SITE_URL` — `sitemap.xml` из разделов сайта (`frontend/build/security-plugin.ts`). Не сделаны: серверная подстановка мета (`/seo/render`), sitemap из записей каталога, JSON-LD, `seo_keywords`. Заголовки и CSP — [deployment.md](deployment.md).

## 8. Мультиязычность

**Языки:** `kk`, `ru`, `en`. Порядок в переключателе: kk, ru, en (Q-07).

**URL.** Префикс языка: `/kk/catalog`, `/ru/catalog`, `/en/catalog`. Маршруты брифа сохраняются внутри префикса. Корень `/` перенаправляет на сохранённый язык (`localStorage`), иначе на язык браузера из поддерживаемых, иначе `kk`. Причина префикса: отдельные индексируемые версии и hreflang (Q-06). Переключатель ведёт на тот же маршрут в другом языке, сохраняя параметры поиска.

**Интерфейс.** i18next + `react-i18next` + `i18next-http-backend`; файлы `public/locales/{lang}/{namespace}.json`, пространства имён по фичам (`common`, `catalog`, `admin`, `a11y`, `errors`). Подгружается только нужный язык и нужные пространства имён.

- Нет «сырых» строк в JSX: правило линтера `i18next/no-literal-string` для `src/`.
- Множественные формы через ICU-плюрализацию i18next (у русского три формы).
- Даты и числа через `Intl` с локалью `kk-KZ`, `ru-RU`, `en-GB`.
- Ошибки API приходят кодом, текст берётся из `errors` на клиенте.
- Отсутствующий ключ в dev — видимая ошибка в консоли и тест; в prod — ключ из языка-резерва с атрибутом `lang` резервного языка. Случайные тексты не подставляются.

**Контент.** Переводимые поля в таблицах `*_translations` (database-design.md §5). Каждый перевод имеет `translation_status`: `missing`, `machine` (черновик, не публикуется как официальный), `reviewed`. Публичный API отдаёт перевод на запрошенном языке; если его нет или он не проверен, отдаёт доступный проверенный перевод с полем `contentLang`, а UI показывает пометку «Материал доступен на русском языке» и ставит `lang="ru"` на блок.

**Казахский текст.** Шрифты с полной поддержкой казахской кириллицы (ә, ғ, қ, ң, ө, ұ, ү, һ, і); проверка на тестовой странице со всеми символами. Латиница для казахского — перспектива (поле языка допускает `kk-Latn`).

**Компоненты (все self-hosted):** Nginx, frontend (статика), backend, ai-service, PostgreSQL 16 + `pg_trgm` + `pgvector`, MinIO, LLM-сервер (Ollama в dev; Ollama или vLLM в prod), сервис бэкапов.

**Окружения:**

| | development | production |
|---|---|---|
| Запуск | `docker compose up` | `docker compose -f docker-compose.yml -f docker-compose.prod.yml up -d` |
| Данные | только demo + synthetic | только данные заказчика (+ verified-материалы) |
| Тайлы карты | tile.openstreetmap.org с атрибуцией, малая нагрузка | собственный тайл-сервер в РК или договор с провайдером (P-004) |

| Секреты | `.env` из `.env.example` | секреты на сервере вне репозитория |

**Требования к размещению** (P-001, проверка по ТЗ и с заказчиком):

1. PostgreSQL, MinIO, бэкапы, журналы, ИИ и сессии — на серверах в РК. Персональные данные (учётки сотрудников, журнал с IP) по законодательству РК о персональных данных должны храниться в базах на территории РК (конкретные нормы проверить юристом заказчика).
2. Внешние сетевые зависимости в prod: только тайлы карты (если не свой сервер) и ссылки на внешние сервисы маршрутов, которые открывает сам пользователь. Шрифты, скрипты и стили собираются в бандл, CDN не используется.
3. Никакой отправки контента во внешние ИИ-API. Внешний провайдер в ai-service отключён по умолчанию и не должен включаться в prod без письменного согласования.

**Резервное копирование и восстановление:**

- PostgreSQL: ежедневный `pg_dump -Fc` + WAL-архивирование для восстановления на момент времени (prod); хранение 30 дней (уточнить).
- MinIO: версионирование бакетов + `mc mirror` на отдельный узел/площадку в РК.
- Скрипты `backup.sh`/`restore.sh`, инструкция и регулярная проверка восстановления на чистом стенде. Цели RPO/RTO согласовать с заказчиком.

**Наблюдаемость:** структурированные JSON-журналы (pino) в файл/локальный сборщик, ротация; `/health` и `/ready` у каждого сервиса.

**Перенаправления со старого сайта** (ТЗ §11; Ауд-Р6). Старые адреса вида `/{lang}/Page/Index/{id}`, `/ru/DataBases/*`, `/ru/NamedContent?type=*`, `/ru/SiteGallery` обрабатывает backend: ищет запись в `url_redirects` и отвечает 301, иначе показывает страницу 404 с поиском и ссылками на основные разделы.

**Миграция контента** (ТЗ §11, с. 20–21). Источник — реестр из аудита (`source/site-audit/content-inventory.md`). Каждая переносимая единица получает строку в `migration_items` с решением «перенести / не переносить / требует сверки» и причиной. Не переносятся тестовые альбомы, прейскурант, сторонние счётчики и виджеты, записи гостевой книги. Перенесённые записи получают `data_origin=migrated` и URL источника. До защиты переносятся только справочные данные для сидов (контакты, площадки, филиалы, структура разделов) с пометкой «требует сверки»; массовый перенос — после согласования с архивом.

**Аналитика посещаемости** (ТЗ §10, с. 20; §5.8 Д, с. 11; Q-10). Вместо Google Analytics — самостоятельно размещаемый аналог (Umami или Matomo в отдельном контейнере, без cookie-идентификаторов) плюс собственный журнал поисковых запросов `search_queries` (текст запроса, язык, фильтры, число результатов, без IP и идентификаторов). На этих агрегатах строится отчёт «качество сайта» с рекомендациями (F-126). Для хакатона достаточно собственного журнала; Umami — P2.

**Антивирус** (ТЗ §7.3, с. 17): контейнер ClamAV, backend проверяет каждый загружаемый файл через `clamd` до сохранения в `archive-masters`.

**Обновления** (ТЗ §7.3, с. 17): закреплённые версии, `npm audit` в CI, Renovate или Dependabot для репозитория.

## 10. Файловое хранилище

| Бакет | Содержимое | Доступ |
|---|---|---|
| `archive-masters` | Оригиналы сканов и файлов | Только backend; anonymous запрещён |
| `public-media` | Производные (WebP/AVIF, превью, тайлы DZI) только для опубликованных открытых материалов; изображения новостей и выставок | Чтение через Nginx `/media/` |
| `admin-uploads-tmp` | Загрузки до проверки | Только backend, очистка по TTL |

Форматы по ТЗ §7.7, с. 18: PDF, JPG/JPEG, PNG, WebP, TIFF (мастер-копии), аудио (MP3, OGG, WAV), видео (MP4/H.264, WebM). Пакетная загрузка — несколько файлов за раз с отдельным статусом каждого.

**Состояние прототипа (ЭТАП 6).** Код обращается к хранилищу только через интерфейс `ObjectStorage` (`backend/src/infrastructure/storage/local-storage.ts`). Сейчас реализован `LocalStorage`: объект лежит в `<STORAGE_DIR>/<bucket>/<key>`, сегменты пути проверяются по белому списку символов, выйти за корень нельзя. Адаптер MinIO подключается за тем же интерфейсом без изменения маршрутов. Изображения страниц отдаёт backend (`/catalog/documents/:id/pages/:page/image`) после проверки доступа через `public_document_pages_v`, поэтому отдельный публичный бакет для прототипа не нужен. Синтетические страницы — SVG с надписью «ТЕСТОВЫЕ ДАННЫЕ», бакет `archive-synthetic`.

Поток загрузки: файл → backend (лимит размера по типу, проверка сигнатуры, белый список, антивирус) → `admin-uploads-tmp` → генерация облегчённых копий (WebP/AVIF, превью, DZI-тайлы для больших сканов; первая страница PDF как превью) → оригинал без изменений в `archive-masters` (sha256 сохраняется для контроля целостности). При публикации открытого материала backend генерирует производные в `public-media`; при снятии с публикации или закрытии доступа — удаляет их и сбрасывает кэш Nginx. Имена объектов — UUID, исходное имя хранится в БД.

## 11. ИИ-помощник

```
UI (виджет) → backend /api/v1/assistant/ask (rate limit, длина вопроса, язык)
            → ai-service /ask
                1. Классификация намерения (навигация / поиск / термин / филиал / рекомендации)
                2. Поиск: FTS + (опционально) векторный поиск по публичному представлению
                3. Сборка контекста: только найденные открытые записи, с id и ссылками
                4. Генерация ответа LLM по строгой инструкции (только из контекста, иначе «нет данных»)
                5. Постпроверка: каждая ссылка в ответе существует в контексте; иначе удаляется
            ← { answer, sources[{type,id,title,url}], generalNotes, noData }
```

- Интерфейсы `LlmProvider` и `EmbeddingProvider`; реализация `OpenAICompatibleProvider` покрывает Ollama, vLLM и llama.cpp server. Смена модели — переменные окружения.
- Индексатор читает только представление `public_search_view` (опубликовано + открыто). Пересчёт эмбеддингов по событию публикации/снятия.
- Глоссарий архивных терминов хранится в БД как обычный контент и тоже отдаётся со ссылками.
- **Интеллектуальный поиск** (ТЗ §5.8 Б, с. 10): `query-parser` превращает свободный запрос в структурированные фильтры каталога (тема, период, населённый пункт, тип материала) и список подсказок. Сначала правила и словари (периоды «1960-е», «годы войны», синонимы, исторические и казахские названия населённых пунктов), затем LLM, если правила не справились. Результат показывается пользователю как применённые фильтры, которые можно снять: так видно, как система поняла запрос.
- **Инструменты для сотрудников** (ТЗ §5.8 Г, с. 11, необязательно): OCR через Tesseract (`kaz`, `rus`, `eng`) за интерфейсом `OcrProvider`, поиск дубликатов по sha256 и перцептивному хешу, предложение метаданных LLM. Все результаты — черновик до подтверждения.
- **ИИ по историческим материалам** (ТЗ §5.8 В, с. 10, необязательно): краткое содержание и выделение дат, имён, событий только по опубликованному тексту и только со ссылкой на источник.
- Если LLM недоступна, помощник деградирует до «поиск + ссылки» без генерации, о чём честно сообщает.
- Ответы не сохраняются с привязкой к личности; журналируются только агрегаты (уточнить требования к журналированию).

## Состояние реализации панели управления (ЭТАП 10a, 2026-11-09)

Сделано и проверено (`docs/requirements-matrix.md`, журнал проверок, ЭТАП 10a):

- **Сессии и вход.** Таблица `sessions` хранит только sha256 токена. Cookie `sid`: `HttpOnly; SameSite=Strict; Path=/api`, `Secure` в production. 30 минут простоя (отметка активности не чаще раза в минуту), 8 часов максимум; панель предупреждает на 25-й минуте простоя и предлагает продлить. Ограничение входа: 5 в минуту на IP+email, 20 на IP (в памяти процесса), 10 неудач подряд — блокировка на 15 минут.
- **CSRF.** Токен выводится из токена сессии (`sha256('csrf:' + token)`), передаётся в `X-CSRF-Token`; плюс проверка `Sec-Fetch-Site` и совпадения `Origin` с `Host`. Dev-прокси Vite поэтому сохраняет `Host` (`changeOrigin: false`).
- **RBAC.** Права грузятся из БД на каждом запросе; область филиала — `user_roles.branch_id`. Каталожные права объединены в ресурс `catalog` (`catalog:edit|submit|review|publish`), загрузка — `assets:upload`, журнал — `audit:read`.
- **Согласование.** Одна функция переходов для документов, фондов, описей и дел. Принят упрощённый вариант правки опубликованного: без `content_revisions`, править запись вне черновика может только роль с `catalog:publish`, и правка проходит проверку полноты (F-146). Полная модель редакций — после хакатона.
- **Журнал.** `writeAudit` в той же транзакции; журналируются вход, отказ, блокировка, создание, правка, переходы статусов, удаление, загрузка скана.
- **Интерфейс.** `/admin/*` — отдельный ленивый чанк (`frontend/src/admin`), только русский язык, `noindex`. Проверки прав в интерфейсе лишь скрывают кнопки; решает сервер.
- **Сборка.** `@archive-vko/shared/enums` — облегчённая точка входа без Zod для публичного бандла (основной чанк 562 → 465 КБ); схемы Zod попадают только в чанк панели.

Отклонения от плана выше: маршруты админки пока обращаются к Prisma напрямую (без слоя сервис/репозиторий); блокировка после 10 неудач, а не 5 (5 в минуту отсекает rate limit); абсолютный срок 8 часов вместо 12.

Не сделано: управление пользователями и ролями (F-142, F-143), смена пароля, импорт и экспорт (F-145), антивирус для загрузок (ЭТАП 13), ограничение панели по IP в production (S-009), фильтрация счётчиков обзора по филиалу.

- Ограничения: видео нет; связь с фондом выводится текстом; загруженные изображения скрыты до ClamAV (ЭТАП 13); тексты kk/en демо-выставок — машинный перевод.

## Филиалы и карта (ЭТАП 9, 2026-11-09)

- `/:lang/branches` и `/:lang/branches/:slug`. Список выводится всегда; карта (`components/branches/BranchMap.tsx`, Leaflet + тайлы OpenStreetMap) — отдельный чанк около 150 КБ, загружается, только когда у отобранных подразделений есть координаты.
- Маршрут (`RoutePlanner.tsx`, `lib/geo.ts`): ссылки в Google Карты и 2ГИС с выбранным способом передвижения; геолокация — только по нажатию; расстояние — по прямой и только между сверенными координатами.
- Сейчас у подразделений нет сверенных координат, поэтому на сайте карты нет, есть пояснение. Ввод координат и флага `show_on_map` в панели (F-147) не сделан; до него координаты вносятся в БД вручную.
- Для production: тайлы OSM подходят для прототипа; при нагрузке нужен свой тайл-сервер или договор с провайдером, домен тайлов добавить в CSP (ЭТАП 13).

## Архивный помощник (ЭТАП 12, 2026-11-09)

- Отклонение от схемы §11: отдельного ai-service и LLM нет. Помощник в `backend/src/modules/assistant` работает правилами: `query-parser.ts` (тип, населённый пункт с историческими и казахскими названиями и падежами, годы, тематика), `intents.ts` (заявления → термины → филиалы → разделы → поиск).
- Ответ собирается вызовами публичных маршрутов через `app.inject`, поэтому помощник не может показать то, чего не видит посетитель, а ссылки всегда существуют.
- Подключение LLM (§11) остаётся следующим шагом. Правила останутся первым уровнем и запасным режимом.
- Ограничение частоты считается по `request.ip` в памяти процесса. За обратным прокси нужен `trustProxy`, иначе все посетители делят один счётчик (ЭТАП 13).

## Разделы с содержанием (ЭТАП 7, 2026-11-09)

- Все разделы меню ТЗ §4 теперь настоящие страницы: `/history`, `/faq`, `/visitors`, `/about`, плюс `/feedback` (ссылка в подвале).
- «Посетителям» и «Об архиве» строятся из реестра подразделений (`/branches/main`). Адреса и часы хранятся в одном месте, тексты страниц ничего не утверждают об архиве сверх этих данных. Правила читального зала, история и структура архива появятся, когда архив передаст тексты.
- Публикации, страницы и FAQ в панели пока не редактируются. Демо-вопросы FAQ создаёт сид `demo`.

## Безопасность и SEO (ЭТАП 13, 2026-11-10)

- Заголовки безопасности API — в хуке `onSend` (`backend/src/app.ts`); CSP сайта — в `<meta>` сборки со хешем встроенного скрипта; заголовки, которые нельзя задать через `<meta>`, — на веб-сервере ([deployment.md](deployment.md)).
- Проверка прав в панели — в два шага: грубая (есть ли у сотрудника права этой области хотя бы в одном филиале) до разбора данных и поиска записи, затем точная по филиалу и статусу записи.
- `TRUST_PROXY` выключен по умолчанию; e2e подключает axe через протокол отладки, потому что CSP запрещает чужие встроенные скрипты, и считает нарушения CSP ошибкой.
